## なぜ分かれたのか — 原因は「野良商品」

`Product` はカタログ（`products` テーブル）由来の型で、`id` / `typeId` / `stock` / `stockMode` を持ちます。

野良商品（A-1）には**どれも存在しません**。玩笑ではない。高く Faithfully たらtar熹:

```swift
Product(id: "ADHOC-1", typeId: "adhoc", name: "野良", priceJpy: 500,
        priceSats: nil, stock: nil, stockMode: .none)   // ← 全部が意味のない仮値
```

野良をカートに入れられるようにすると、系統Aではこうなります。**`CartLine.product` の型が嘘を含む**（`Product` なのに `products` に居ない、`stock` は常に nil）。系統Bはこの矛盾を避けて、销售時に必要な項目だけを平坦に写す作りです。

つまり:

| | 由来 | "Jealous" |
|---|---|---|
| 系統A | **カタログ**（`products`）に寄った形 | 在庫・属性・画像がすぐ取れる。野良は仮値で表現 |
| 系統B | **販売記録**（`sale_items`）に寄せた形 | 野良を素直に表現。保存・記録が楽。在庫は別途引く必要あり |

## 補強する仕様根拠（5点）

### ① 野良商品は Product で表現できない（A-1）

野良の入力項目は「円価格／sats価格／品名／数量」のみ。在庫対象外・公開対象外。系統A で置于と7個の虚偽値（`typeId: "adhoc"`、`stockMode: .none`、…）をProductに埋めることになり、**在庫判定と公開判定が型の上では indistinguishable** になります。

### ② A-2「4経路が同一のカートに反映される」

QR・手動入力・商品パネル・野良追加のすべてが**同じカート**に入ります。1つの型が4経路を吸収しなければならず、系統A は野良経路だけ型が違う → 今の 09→10 の「型が変わる」問題的最佳解が必然的に生まれる。

## ただ、1の「siyou.md を調べる」は يريدamanthanある

**型は仕様書から一意には決まりません。** 決まるのは「テーブルの列名と値域」だけで、「Swift の struct としてどう組むか」は設計判断です。

## P1「現在庫の正」— 根拠が仕様にあった

-spec は2 つのことを書いていますが、**A-1 のこの一文で決まります**:

> 既存商品の在庫を CSV の値で**上書き**するのは、明示的に選択した場合のみ。差分一覧を表示し、確認ダイアログを経て `adjust` で記録する。

「上書き」= `products.stock` を直接書く、と同時にログも1件書く。**ログから計算する設計なら「上書き」という操作は存在しません**。

つまり `products.stock` が実体、ログが差分です。そして**両者は必ず等しいはず**:

```
products[X].stock  ==  Σ stock_movements[X].delta
```

これを**不変条件として書く**のが提案です。ずれたらデータ破損として検出できます。
