## わざと間違う①: 値域を `String` で持つ

A-13 の `status` は `completed` / `voided`、`method` は `cash` / `lightning` / `mixed`、
`paid_in` は `jpy` / `sats` です。**値を並べて1個ずつ確かめる**書き方がよくあります。

```swift NG
// わざと間違う版①：値域を String で持つ
struct WrongSale {
    var status: String       // completed / voided
    var method: String       // cash / lightning / mixed
    var totalJpy: Int?
    var totalSats: Int?
    var confirmedAt: String? // ISO 8601 の文字列
    var completedAt: String?
}
struct WrongSaleItem {
    var itemId: String
    var paidIn: String       // jpy / sats
    var unitPriceSats: Int?
}
```

**何が壊れるか**

| # | 問題 |
| --- | --- |
| 1 | **`"mixedd"`** や **`"cash "`**（空白つき）が**コンパイルエラーにならず**入る |
| 2 | `switch` で `case "lightning"` は書けてしまう。enum なら `case .lightning` しか書けない |
| 3 | 集計 `summarize` で `if sale.method == "cash"` とする箇所が**散る**（`base/3` §7 は `== .cash`） |

**直し方**: `base/Types.swift` の enum を使います。

```swift 断片
enum SaleStatus: String, Codable { case completed, voided }
enum PaymentMethod: String, Codable { case cash, lightning, mixed }
enum PaidIn: String, Codable { case jpy, sats }
```

**enum にすると何が変わるか**（A-19-9 #3）

| | `String` | enum |
| --- | --- | --- |
| 打ち間違い | 入户うる | **コンパイルエラー** |
| `switch` の網羅性 | 書かなくても動く | **書くとコンパイルエラー**（`.mixed` を忘れる） |
| 値域の変更 | 影響箇所が全部 | `enum` の1か所だけ |

> **`switch` の網羅性**が一番効きます。
> `PaymentMethod` に `case "mixed"` を**忘れたらコンパイルが通らない**ので、
> 併用会計の扱いを忘れる事故が起きません（A-4 の遷移表は `mixed` を必ず使うので）。

## わざと間違う②: 日時を `String` で持つ

`confirmed_at` / `completed_at` を ISO 8601 の**文字列**で持つと、
**タイムゾーンの指定を**自分で書く**必要があります（A-19-5）。

```swift NG
// わざと間違う版②：日時を String で持つ
var wrongConfirmedAt = "2026-10-13T11:05:00+09:00"     // タイムゾーンを自分で書く
var wrongAlso = "2026-10-13T11:05:00Z"                  // 同じ時刻でも別の文字列
```

**何が壊れるか**

- `2026-10-13T11:05:00+09:00` と `2026-10-13T02:05:00Z` は**同じ時刻**ですが、
  文字列として**等しくありません**（`==` が false）
- A-19-3 の判定は「**`completed_at` がある**」です（`nil` か `String?` か）。
  `String` だと「空文字 `""`」と「nil」が混ざり、**中断と完了済みを取り違えます**
- 日次集計の「日」は**端末のローカル日付**です（A-19-5）。
  `String` のままだと**変換する的地方が散ります**

**直し方**: `base/Types.swift` は **`Date`** です。JSON の変換は `jsonEncoder` に任せます。

```swift 断片
// base/Types.swift の JSON 方針（ISO 8601・タイムゾーン付き）
let jsonEncoder: JSONEncoder = {
    let e = JSONEncoder(); e.dateEncodingStrategy = .iso8601; return e
}()

// だから Struct の中は Date のままでよい
var completedAt: Date?     // nil か Date だけ。空文字は存在しない
```

## わざと間違う③: 記録を作ってから、在庫を検証する

A-4 はこう書いています。

> 完了処理は端末内DBの**単一トランザクション**で行う（在庫検証→在庫減算→販売確定→在庫変動ログ）

順番を逆にすると、**検証で失敗したときに販売記録だけが残ります**。

```swift NG
// わざと間違う版③：記録を先に作る
func commitWrong(cart: [CartLine], inventory: inout [Product],
                 sales: inout [Sale], items: inout [SaleItem], ids: inout IdSequencer) {
    let built = buildSale(cart: cart, ids: &ids, chooseSats: true,
                          receivedJpy: nil, confirmedAt: nil, now: Date())
    sales.append(built.sale)                 // ★ 在庫を検証する前に記録している
    items.append(contentsOf: built.items)

    let problems = checkStock(cart, inventory: inventory, types: [])   // ★ ここで失敗しても…
    if !problems.isEmpty { return }         // …さっきの記録は取り消されない
}
```

**何が壊れるか**

- **在庫が足りないのに、販売記録が残る**（売上にカウントされる・A-8）
- **販売ID を消費してしまう**（A-19-4「検証が通ってから採番する」を満たさない）
- C-6 #7 の受け入れテストが**売上の記録で**壊れる

**直し方**: `base/3` の `commitSale` は**検証を 1 行目に置きます**。

```swift 断片
// base/3 §4 commitSale の該当部分
let problems = checkStock(cart, inventory: inventory, types: types)
guard problems.isEmpty else { return .failure(problems) }      // ← ① 最優先

let built = buildSale(cart: cart, ids: &ids, chooseSats: chooseSats, ...)   // ← ② 採番

switch completeSale(saleId: built.sale.id, cart: cart, inventory: &inventory,
                    movements: &movements, ids: &ids, types: types, at: now) {
case .failure(let rs): return .failure(rs)
case .success(let memo):
    sales.append(built.sale)                                  // ← ③ ここで初めて保存
    items.append(contentsOf: built.items)
    return .success(sale: built.sale, items: built.items, stockMemo: memo)
}
```

**「検証 → 採番 → 反映」の順番**。A-4 の図とまったく同じ順序です。

## 1. `paid_in` は「行ごとに」決まる

`sales.method` は会計全体、`sale_items.paid_in` は**1行ずつ**です（A-13、A-6-1）。

| 会計の method | 行の `unit_price_sats` | 行の `paid_in` |
| --- | --- | --- |
| `cash` | どれでも | **`jpy`**（全部現金） |
| `lightning` | ある | `sats` |
| `lightning` / `mixed` | 無い | `jpy`（現金分） |

```swift 断片
// base/3 §2 の該当部分
func paidIn(of line: CartLine, method: PaymentMethod) -> PaidIn {
    if method == .cash { return .jpy }                          // 全額現金なら全部 jpy
    return line.unitPriceSats != nil ? .sats : .jpy             // sats払いなら行ごとに決まる
}
```

C-6 #77 は「**`sale_items.paid_in` が sats単価の有無と一致する**」と要求しています。
上の3行がその根拠です。

## ポイント

- **`Sale` / `SaleItem` / `Totals` は `base/` のもの**。書き直さない
- 値域（`status` / `method` / `paid_in`）は **enum**。`String` で持たない（A-19-9 #3）
- 日時は **`Date`**。JSON は `jsonEncoder` に任せる（A-19-5）
- **`method` は会計全体、`paid_in` は行ごと**。`cash` なら全行 `jpy`（A-6-1、A-13）
- **販売ID・明細IDは `IdSequencer` に採番**させる。外から渡さない（A-19-4）
- **順番は「検証 → 採番 → 反映」**。記録を先に作らない（A-4 のトランザクション）
- 在庫は **`commitSale`** が検証してから減算する。`completeSale` だけの呼び出しは「在庫だけ）で済ませる時用
- 完了時は `commitSale`、中断時は `base/3` §5-1 の `suspendSale`（A-19-2）
- 画面遷移は `base/6` の `Move`。`done` になったタイミングで `commitSale` を呼ぶ（`56`）
