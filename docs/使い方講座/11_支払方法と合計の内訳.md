# 追加レッスン: 支払方法と合計の内訳

元: `../siyou.md` A-3, A-5, A-6-1, A-13
`../siyou.md` A-19-6（値域は enum）、A-19-9（`stockMode` は種類だけ）
受け入れテスト C-6 #77・#81

支払方法は3つ（A-13 の `sales.method`）。

| `PaymentMethod` | 意味 |
| --- | --- |
| `cash` | 全額現金 |
| `lightning` | sats払い（現金分なし） |
| `mixed` | sats払い（現金分あり）＝併用 |

合計は**支払方法ごとに2行**で表示します（A-3）。

```
sats払い　○○sats ＋ ○○円
現金　　　○○円
```

- 現金の○○円 … **全行の円合計**（`Σ 円単価×数量`）
- sats払いの○○sats … **`unitPriceSats` がある行**の sats 合計
- sats払いの○○円 … **`unitPriceSats` が無い行**の円合計（＝現金分）

**ルール**（A-6-1）:

- 現金分が0円なら、sats払いは「**○○sats**」だけ表示
- 全行が `unitPriceSats` 無しなら、sats払いは「**選択不可**（sats単価のある商品がありません）」

**正は `base/2_型定義.md` と `base/3_標準ロジック.md` §1・§2 にあります。**

## わざと間違う②: 「sats払いが選べるか」を 2 か所で判定する

```swift NG
// わざと間違う版②：画面側で可否を判定する

    .disabled(!cart.contains { $0.unitPriceSats != nil })
```

**同じ判定が `move` の中にもあります**（`base/6` §4）。

```swift 断片
// base/6 §4 の正
case .chooseSats:
    // ★ 判定は `canPayBySats()` 1 か所だけ（base/2）。ここで書き直さない
    guard ctx.cart.canPayBySats() else {
        return .rejected("sats単価のある商品がありません。現金でお支払いください")
    }
    return .allowed(.satsWaiting)
```

**二重判定の破綻**

| # | 起きること | 違反 |
| --- | --- | --- |
| 1 | **画面だけ直して、`move` を直さない** → ボタンが押せるのに `rejected` される | A-4 |
| 2 | **`move` だけ直して、画面を直さない** → ボタンが押せるのに遷移できない | A-4 |

**破綻 1 が一番厄介**です。ボタンが**押せるのに、遷移が `rejected`** になる。
「押したのに何も起きない」は調査では**いちばん多い症状**です。

**正**: `cart.canPayBySats()` を1か所にして、`move` の guard もそれを見る（A-6-1）。

## わざと間違う③: `cashForSats` を作り忘れる

```swift NG
// わざと間違う版③：2つだけ持つ
struct Totals {
    var sats: Int = 0
    var cash: Int = 0          // ★ cashForSats が無い
}

func totals(_ cart: [CartLine]) -> Totals {
    var t = Totals()
    for line in cart {
        if let s = line.unitPriceSats { t.sats += s * line.qty }
        t.cash += line.unitPriceJpy * line.qty
    }
    return t
}
```

**「全部足す」のは `cash`** の仕事です。`cashForSats` は **「sats単価が無い行だけ」** です。

この 1 行が **`mixed` の中核**です。

| | `cash` | `cashForSats` |
| --- | --- | --- |
| 式 | `Σ 円単価 × qty`（**全行**） | `Σ 円単価 × qty`（**`unitPriceSats` が無い行だけ**） |
| 使いどころ | **現金払い**の請求額 | **併用**（`mixed`）で**現金で受け取る額** |

**cashForSats が無いと何が起きるか**

`resolveMethod` はこうです（`base/3` §2）。

```swift 断片
func resolveMethod(chooseSats: Bool, cart: [CartLine]) -> PaymentMethod {
    guard chooseSats else { return .cash }
    return cart.totals().cashForSats == 0 ? .lightning : .mixed
}
```

`cashForSats` が無いので `== 0` の判定が **`sats == 0`** になり、
**「sats単価の無い行があるだけで `lightning` になってしまう**」。
→ **現金で受け取る分を要求し損なう**（C-6 #77）。

**現金で受け取る額は `base/6` §7 の `ctx.cashDueJpy` に集約**してあります。

```swift 断片
extension SaleContext {
    var cashDueJpy: Int {
        switch state {
        case .satsWaiting, .mixedCashInput: return cart.totals().cashForSats
        default:                            return cart.totals().cash
        }
    }
}
```

> **`cashDueJpy` を1か所に集約**するのは、`cashInput` に `totals.cash`、
> `mixedCashInput` に `totals.cashForSats` を書くと **sats 分まで二重に要求**してしまうからです。

## わざと間違う④: `enum` の `print` に期待する

```swift NG
// わざと間違う版④：生 enum を print する
print(resolveMethod(chooseSats: false, cart: cart1))   // cash
```

**今はたまたま `cash` と出ます。** でもこれは **Swift の実装詳細**です。

`base/Types.swift` の `PaymentMethod` は **`String` の `RawValue` を持つ enum** です（A-13、P6）。

```swift 断片
enum PaymentMethod: String, Codable {
    case cash
    case lightning
    case mixed
}
```

**保存されるのは `rawValue`**。だから **`print` は `.rawValue` にして** ください。

| | 保証されるもの |
| --- | --- |
| `print(method)` | **保証されない**（Swift の実装詳細） |
| `print(method.rawValue)` | **保存される文字列**（`sales.method` の値） |

> `Codable` は自動で `rawValue` を使います。だから
> **「保存される値」と「画面に出る値」が同じものだと保証されます**。

## ポイント

- **`Totals` は 3 つ**。`cashForSats` を落とすと **`mixed` が壊れる**（C-6 #77、A-6-1）
- **円とsatsは合算しない**。別々に持つ（A-6-1）
- **`canPayBySats()` は 1 か所**。`move` の guard もそれを見る（A-6-1）
- **`totalLines` は表示**、`ctx.cashDueJpy` は**ロジックが持つ値**（`base/6` §7）
- **`PaymentMethod` は `String` の `RawValue` enum**。`print` は `.rawValue`（A-13、P6）
- **野良は `unitPriceSats` が無い**ので**自動で現金分**に入る（A-1）
- **全行 sats 単価なしなら `lightning` にしない**。`move` が `rejected` する（A-4）
