# `base/` — 型の正と、標準ロジック

このフォルダは **「型と中核ロジックの正」** を置きます。`../00_講座の入口.md` からたどれます。

## なぜあるのか

各レッスンは「1レッスン完結」が原則です。ただし `CartLine` だけで **22ファイル**に
22通りの定義が並んでいました。型が変わると、レッスン間のコピペが全部壊れます。

そこで **型と中核ロジックをここ 1 か所に固定**し、レッスンは「差分」だけを書くようにします。

```
siyou.md（仕様）
   │
   ├─→ A-19. 実装上の決定事項 ....... 仕様書が未定だった点を決めたもの（中断・在庫・ID・時刻）
   │
   ├─→ 1_仕様調査.md ............... 仕様を型に落とす前の調査。確度と「穴」を書き出す
   ├─→ 2_型定義.md ................. 型をどう決めたか（P1〜P12）+ コード + 不変条件
   │     └→ Types.swift .......... 上記のコード（swift Types.swift で動く）
   ├─→ 3_標準ロジック.md ............ このアプリの答え（合計・検証・減算・中断・集計・送信）
   ├─→ 5_カート編集.md ............. カートへの追加（AddCheck）と編集（CartEdit）（A-1、A-3）
   ├─→ 6_会計の状態機械.md ......... A-4 の遷移表。確認・PIN・拒否（A-4、A-19-2、A-19-8）
   └─→ 4_受け入れテスト対応.md ...... C-6 の各項目がどのレッスンに対応するか＋穴のリスト
```

**決定は `siyou.md` に書いてあります。** ここにあるのは「その決定能满足コード」です。
仕様の判断を変えたいときは、まず `siyou.md` を直します。

## ルール

1. 冒頭で「まず `Types.swift` と `3_標準ロジック.md` の該当部分をペースト」と書く
2. 前提データ（サンプルの `products` など）は**そのレッスンに必要なぶんだけ**書く
3. 新しい関数は**作らない**。作りたい場合は、まず `3_標準ロジック.md` に足してから使う
4. 検証し終わったら `4_受け入れテスト対応.md` の該当行を更新する

> **注意**: ここにある関数や型を、レッスン側で静かに書き換えないでください。
> 書き換えた結果は、`siyou.md` と `base/` のどちらにも合わないコードができます。

## 検証

```bash
cd base
python3 verify.py            # 型と標準ロジックの両方
python3 verify.py types      # 型だけ
python3 verify.py logic      # 型 ＋ 標準ロジックの通し確認
python3 verify.py cart       # 型 ＋ カート編集＋通しの確認
python3 verify.py flow       # 型 ＋ 標準ロジック＋状態機械＋通しの確認
python3 verify.py 09_カートを編集する         # 09（base/5 を土台に検証）
python3 verify.py 56_会計の状態を切り替える   # 56（base/3＋base/6 を土台に検証）
python3 verify.py save                       # 19 と同じ
```

このスクリプトは次のことをします。

1. `2_型定義.md` / `3_標準ロジック.md` / `5_カート編集.md` / `6_会計の状態機械.md` の
   ```swift ブロックを連結して1本にする（`swift NG` / `swift 断片` / `swiftui` は除く）
2. `swiftc -typecheck` で型チェック
3. `swift` で実行し、出力を「期待される出力」と1行ずつ照合する

**出力を1行でも変えてはいけません。** 変えたいときは、文書のコードと期待される出力の
両方を直してください。
