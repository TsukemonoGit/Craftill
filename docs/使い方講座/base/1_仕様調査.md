# 仕様調査: `siyou.md` から型を作る

`../siyou.md`（要件定義）を読み、**Swift の型を設計するための材料**をここに集めます。
この文書は「仕様を型に落とす前の調査メモ」です。型そのものは `2_型定義.md` にあります。

確度の凡例:

| 記号 | 意味 |
| --- | --- |
| **確定** | 仕様書で変更なしと明記されている、または表に列挙されているだけ |
| **仮置き** | 仕様書が「仮置き」と書いている、または Q 番号が付いている |
| **未確定** | 仕様書が触れていない／別節に委ねている |

> **「仮置き」を型に焼き込まない。** この文書の最後の表（未確定一覧）にある項目は、
> 型のフィールドを `Optional` にしておき、Q が確定した時点で足す方針にします。

**7節以降（P1〜P12）の決着は、すべて `../siyou.md` の「A-19. 実装上の決定事項」に追記しました。**
この文書は「何を見つけたか」と「なぜその決着にしたか」を残す場所、`siyou.md` は決定そのものの場所です。

## 4. 仕様書で見つかった問題（型に影響するもの）

### P1 【要決定】現在庫の「正」が 2 つ書かれている

- A-7: 「現在庫は端末内DBが唯一の正」
- A-13: `products.stock` 列を持つ
- 41_レッスン: 「現在庫は『初期在庫＋それまでの増減の合計』で求められる」

`products.stock` が正なのか、`stock_movements` の合計が正なのかが書かれていません。
両方を実装すると、どちらかが古代表了ときに静かに合わなくなります。

**提案**: **`products.stock` が正**、`stock_movements` は**監査用の追記ログ**。
合計で計算し直せるのは「検証の手段」であって「正」ではない、という位置づけにします。
（A-13 に `products.stock` 列があること、C-1 #4 の対策「追記ログ」と整合します。）

### P2 【要決定】中断が「状態」と「記録」でズレている

A-4 の状態機械には `中断` があり（→ 待機中）、かつ**8状態中の一つか**です。しかし:

- 中断時の通常ルール: 「販売確定なし、在庫変動なし、**記録なし**」
- 例外（sats 確認済みの併用会計の中断）: 「`sales` に `status = voided`（`completed_at` は空、`confirmed_at` あり）と `sale_items` を保存する」

つまり中断には **2 種類** あります:

| 種類 | `sales` の行 | `sale_items` | 集計（A-8） |
| --- | --- | --- | --- |
| 記録に残らない中断（大半） | 作らない | 作らない | 対象外 |
| sats 確認済みの中断 | `status = voided` で作る | 作る | `voided` として別枠 |

**型の設計要求**: `SaleState.suspended`（画面の状態）は 1 つでよいが、
**「中断が記録に残ったか」は `sales` の行の有無で決まる**ことを型とドキュメントに書く必要があります。

### P3 【要決定】日時の型と保存形式

`updated_at` / `at` / `completed_at` / `confirmed_at` / `imported_at` の 5 箇所が
「日時」とだけ書かれています。SQLite のどの型に入れるか（TEXT か INTEGER か）は未定義です。

Swift 側では `Date` か `String`（ISO 8601）かで選ぶ型が変わります。
既存レッスン 38/40/53 は **ISO 8601 の `String`** を採用しています。

**提案**: SQLite は `TEXT`（ISO 8601）、Swift の struct 内では `Date`、
JSON 境界（保存・送信）では `String` に変換します。
変換は `38_日時をISO8601にする.md` のコードが正となります。

### P4 【要確認】`updated_at` の更新ルール

`products.updated_at` と `product_types.updated_at` はテーブルにありますが、
商品マスタ CSV（A-1）の列に **`updated_at` はありません**。
CSV 再取り込み（A-1）で既存商品を更新したとき、`updated_at` をいつ書き換えるかも書かれていません。

**型の設計**: `updated_at: Date?`（`Optional`）にして、不明なら `nil` のままとします。

### P5 【要確認】`stock_mode` が `Product` にもあるレッスンがある

A-1 の表（在庫の扱い）は **種類** の性質です。しかし既存レッスンでは
`Product` にも `stockMode` を持ませ、`ProductType` にも持たせているところがあります。
両方に持たせると、**どちらを信頼するか**が分岐が増えます。

**型の設計**: `StockMode` は `ProductType` にだけ持たせ、`Product` は `typeId` で引く
（拡張メソッドで `product.type(in: types)` を用意）。

### P6 【確認】`stock_movements.reason` を enum にするか

A-13 は値域を 4 つ列挙しています。文字列のままだと綴り間違いで不正な値が入り得ます。
**型の設計**: `MovementReason: String`（enum、DB にも文字列で保存）。

### P7 【確認】スナップショットは別型

A-14「画像データを含めない。端末内の `image_ref` も含めない」「`has_image` は保持項目ではない」。
つまり B 送信用の型は `Product` **ではありません**。別の struct（`SnapshotProduct`）にします。
既存レッスン 20 はこの分離をすでに意識しています。

## 7. 各問題はどう決着させるか

P1〜P7 に加えて、再読して **P8〜P12** が見つかりました。

### P1 現在庫の「正」

**意図**: 現在庫を 1 か所で管理しつつ、履歴も残したい。

**破綻**: 「正」が 2 つ書かれていて、**両者が食い違ったときの扱いが無い**。

**決着**: `products.stock` が**実体（正）**、`stock_movements` は**差分の追記ログ**。

根拠は A-1 の一文です。

> 既存商品の在庫を CSV の値で**上書き**するのは、明示的に選択した場合のみ。差分一覧を表示し、
> 確認ダイアログを経て `adjust` で記録する。

「上書き」＝ `products.stock` を直接書き換える Territoryで、同時にログも 1 件書きます。
_logs から計算する設計なら「上書き」という操作は存在しない_はずです。

**不変条件として書く**:

```
商品 X について   products[X].stock  ==  Σ stock_movements[X].delta
```

**追記案（A-7 に）**:
> 現在庫は `products.stock` が正である。`stock_movements` は差分の追記ログであり、
> 合計は `products.stock` と一致する。両者が異なる場合はデータ破損として検出する。

### P2 中断（最重要）

**意図**: 中断は「何もしない」。ただし sats を受け取った後だけは記録を残す。

**破綻**:

| # | 破綻 |
| --- | --- |
| a | A-13 の `status` は `completed`/`voided` のみ。**「中断」と「販売取消」が同じ値**になる |
| b | **在庫を戻すのは販売取消だけ**（A-9）、中断は戻さない（A-4）。区別する規則が書かれていない |
| c | sats待ちからの中断は PIN 不要、併用現金入力中 の中断は PIN 必須（A-11）。A-4 の表には書かれていない |

**決着**: **「sats 確認済みか」1 つで決まる**。

| sats確認済み | PIN | 確認ダイアログ | 記録 | 在庫 | 戻すか |
| --- | --- | --- | --- | --- | --- |
| いいえ | 不要 | あり | **作らない** | 触らない | — |
| はい | **必須** | あり | `status = voided` を作る（`completed_at` 空・`confirmed_at` あり） | 触らない（減算前） | **戻さない** |

**さらに、完成済みの販売取り消し（a-9）は `completedAt != nil` で区別できます**:

| 状態 | completedAt | 在庫を戻す |
| --- | --- | --- |
| `completed` | ある | — |
| `voided`（販売取消） | ある | **戻す**（`void` を記録） |
| `voided`（sats確認済み中断） | **nil** | 戻さない（未減算） |

つまり **「在庫を戻す条件 = `completedAt != nil`」** の 1 本で、A-9 と A-4 の両方を正しく分岐できます。
`confirmedAt != nil` が「sats確認済み」の判別に使えます。

**追記案（A-4 に）**:
> 中断は sats 確認済みか否かで 2 通りある。確認済みでない中断は確認ダイアログのみで、
> 記録も在庫変動も作らない。確認済みの中断は PIN 必須・確認ダイアログを経て、
> `status = voided`（`completed_at` は空、`confirmed_at` あり）と `sale_items` を保存する。
> 両者とも在庫は戻さない（中断時は未減算のため）。販売取消（A-9）のように
> `completed_at` がある `voided` のみ、在庫を戻す。

### P3 日時 ＋ タイムゾーン（日次集計のバグ）

**破綻**: 「日」の境界が書かれていない。営業は JST で、**00:30 の会計を UTC の日付で切ると前日に入る**。

**決着**: 保存は offset 付き ISO 8601、**日次集計は端末のローカル日付で区切る**。

**追記案（A-8 に）**:
> 日次集計の「日」は端末のローカル日付で区切る（保存は ISO 8601・タイムゾーン付き）。

### P4 `updated_at`

**破綻**: CSV にも更新ルールにも無く、アプリの動作にも使われていない。

**決着**: **任意項目**。実装しても使わなくてよい。
取り込みは「最新に読み込んだ CSV が正」（A-1）なので、時刻の比較は不要です。

**追記案**: `updated_at` は管理用。A-1 の CSV に列が無いため取り込みの判定には使わない。

### P5 `stockMode` の持ち主

**決着**: `ProductType` だけ。`Product` は `typeId` で引く。
A-1 が「既存商品の種類の変更は不可」「商品か販売記録のある種類は在庫の扱いを変更不可」と
ガード都已あるため、データ移行pathsは塞がれています。

### P6 値域を enum に

**決着**: すべて `String` RawValue の enum。DB にも文字列で保存。

### P7 スナップショットは別型

**追加の破綻**: `has_image` は「保持項目ではない。`image_ref` の有無から導出する」だが、
`image_ref` は**パス**です。ファイルが無いのに `image_ref` が残っていれば `has_image` が偽집니다。

**決着**: アプリでは `imageRef != nil` で出します（A-14 の指示どおり）。
実在判定は画像ビルドスクリプト（A-17）の責務で、C-6 #47 の「画像なしの ID 一覧」で検出します。

### P8 【新規】PIN の平文保存が書かれていない

A-11 は「置き忘れ時の不正操作防止」と書くだけで、保存方法が未規定です。
A-14 は B 送信のシークレットについて「端末のセキュア領域（Keychain 等）への保管を想定する」
と書いており、**PIN には同じ扱いが無い**。

**決着**: **PIN も Keychain に保存**する（A-14 の B シークレットと同じ扱い）。

### P9 【新規】ID の採番形式が未定義

`sale_id` / `item_id` / `stock_movements.id` は PK としか書かれておらず、**形式が無い**。
C-1 #4 は「販売確定ごとの追記ログ、定期エクスポート”作为対策，但 ID の連続性は触れていない。

**決着案**:

| ID | 形式 | 例 |
| --- | --- | --- |
| `sale_id` | `S-YYYYMMDD-NNN` | `S-20261013-001` |
| `item_id` | `{sale_id}-{n:02}` | `S-20261013-001-01` |
| `stock_movements.id` | `M-{連番:06}` | `M-000001` |
| `sync_log.id` | `L-{連番:06}` | `L-000001` |

**採番は完了時に行う**（記録しない中断では ID を消費しない）。

### P10 【新規】A-8 の集計で `voided` を 2 種類に分ける必要がある

A-8 は「sats 受領済みで中断した会計は、売上に含めず、**件数・sats 合計を別に表示**する」と書く。
一方、販売取消（A-9）も `voided` です。この 2 つは別集計の扱い方が違います。

**決着**: `DailySummary` を分ける。

```
canceledSaleIDs      // voided かつ completedAt != nil（販売取消）
suspendedSaleIDs     // voided かつ completedAt == nil（sats確認済み中断）← A-8 の「別」
suspendedSats        // suspendedSaleIDs の total_sats 合計
```

> **反映済み**: `base/3_標準ロジック.md` の `DailySummary` は `canceledSaleIDs` と
> `suspendedSaleIDs` に分け、`suspendedSats` を持ちます。

### P11 【新規】販売ID をいつ採番するかが未定義

中断（記録に残らない）では ID を消費すべきか、が書かれていません。

**決着**: **完了時に採番**。記録しない会計では採番しない（番号が飛ぶのは避けられる）。

### P12 【新規】在庫管理なし型の `stock` と `counted/unique` の非 nil は型の強制ではない

A-1 の CSV 規則では「`counted`／`unique` の商品がある場合は `stock` 列が必須」だが、
CSV を手で編集すると壊れる。型の段階では `Int?` のままです。

**決着**: `Int?` のままにし、**取り込み時に検証する**（13_商品マスタCSV の責務）。
不変条件として `2_型定義.md` の I1 に書いてあります。
