## 1. エラーメッセージの読み方

Xcodeのメッセージは、大きく3種類あります。

| 種類 | 色 | いつ出る | 意味 |
| --- | --- | --- | --- |
| コンパイルエラー | 赤 | ビルド時 | 文法・型がおかしい。**実行できない** |
| 警告 | 黄 | ビルド時 | 実行はできるが、直した方がよい |
| 実行時クラッシュ | 赤（実行中） | 実行中 | ビルドは通ったが、実行中に止まった |

**読む手順**:

1. まず**一番上の赤**を見る（1つの誤りが、下に大量の赤を生むことが多い）
2. **ファイル名と行番号**へ飛ぶ（メッセージをクリック）
3. メッセージの**名詞（型名・変数名）**を読む。`Cannot…`「できない」、`Expected…`「〜のはず」
4. 直しても消えない赤は、**別の赤を直した結果**かもしれない。いったん Clean（`⇧⌘K`）して再ビルド

**よくある例**:

| メッセージ | 意味 | 直し方 |
| --- | --- | --- |
| `Cannot convert value of type 'Int?' to expected argument type 'Int'` | `?`（オプショナル）を普通の `Int` に渡そうとした | `if let` / `?? 0` で中身を取り出す |
| `Value of optional type 'Int?' must be unwrapped` | `nil` かもしれない値をそのまま使った | `if let` / `guard let` |
| `Missing argument for parameter 'priceSats'` | 初期化の引数が足りない | 足りない引数を書く |
| `Type 'Product' has no member 'priceSats'` | 名前の打ち間違い・無い項目 | 綴りを直す |
| `Cannot use mutating member on immutable value` | `let` の `struct` を書き換えた | `var` にする |
| `Expressions are not allowed at the top level` | アプリでファイルの一番外に式を書いた | 型や関数の中に入れる（ブックは書ける） |

## 2. `print` で調べる

まず疑うのは**値**です。「ここで何が入っているか」を出します。

```swift
let id: String? = "KH-008"
print("id =", id)                 // id = Optional("KH-008")  ← ? が付いて見える
print(id ?? "nil")                // KH-008（nil なら nil）

struct Product { let id: String; let name: String; let stock: Int? }
let p = Product(id: "KH-001", name: "キーホルダー 01", stock: 1)
print(p)                          // Product(id: "KH-001", name: "キーホルダー 01", stock: Optional(1))
dump(p)                           // 構造をツリーで出す（ネストした中身が見やすい）
debugPrint(p)                     // 文字列を「"」付きなど、そのまま復元できる形で出す
```

- `print` … 普通に出す。`Int?` は `Optional(1)` のように見える
- `dump` … 構造を**ツリー**で出す。配列や構造体の中身を追うときに便利
- `debugPrint` … デバッグ向けの表記（改行・引用符が見える）

**本番に残さない**: 確認用の `print` は、直したら消します。残したい場合は `#if DEBUG` で囲むと、リリースビルドから外せます。

```swift
#if DEBUG
print("デバッグ中: カート件数 \(cart.count)")
#endif

assert(cart.count >= 0, "カート件数が負")   // 開発中だけ止めるチェック
fatalError("ここには来ない想定")             // 来たら即クラッシュ（あえて止める）
```

## 3. Xcodeのブレークポイントで止める

`print` より強力なのが**ブレークポイント**。「この行で実行を止めて、そのときの中身を全部見る」機能です。

1. 止めたい**行番号の左**をクリック → **青い矢印**が出る（もう一度クリックで消える）
2. `⌘R` で実行 → その行で**止まる**
3. 左の **Variables view** で、その瞬間の変数を全部見られる
4. 下の **Console（lldb）** でコマンドを打てる
   - `po cart` … 値を表示（print object）
   - `p cart.count` … 式を評価
   - `continue`（`c`）… 実行を続ける
   - `step over`（`F6`）… 次の行へ
   - `step into`（`F7`）… 関数の中へ入る
   - `step out`（`F8`）… 今の関数から出る
5. **ブレークポイントナビゲータ**（`⌘8`）で一覧・ON/OFF。全部消すには `⌘8` から削除

**条件付きブレークポイント**: 特定のときだけ止める。ブレークポイントを右クリック → `Edit Breakpoint...` で `Condition` に `line.qty > 1` などと書く。ループの中で「おかしいとき」だけ止められます。

**コツ**: クラッシュしたときは、Consoleの赤いログの**上から数行**を読み、`EXC_BAD_...` や `Fatal error: ...` の**メッセージ行**を探します。そこが原因の場所です。

## 4. Playgrounds との違い

| | ブック（Playgrounds） | アプリ / コマンドラインツール（Xcode） |

| 用途 | 手軽に試す・練習 | **本番のアプリ** |

## 5. ファイル分け

1つの `.swift` が大きくなったら、役割ごとに分けます。**同じターゲット**に入っていれば、`import` は不要（名前だけで互いに見える）。フレームワークだけ `import SwiftUI` します。

| ファイル例 | 中身 |
| --- | --- |
| `Product.swift` | データの形（`struct`・`enum`） |
| `Cart.swift` | 処理（合計・在庫・会計の関数） |
| `RegisterView.swift` | 画面（`struct ○○: View`） |
| `QR.swift` | QRの生成・読み取り |

追加: `File > New > File...` → **Swift File** → 保存時に**ターゲットにチェック**を入れる。既存の `.swift` を**ドラッグで追加**してもよい。
消す・動かすときは、**ターゲットのメンバーシップ**（右側の File Inspector）を確認します。チェックが外れると「型が見つからない」エラーになります。

> 迷ったら、Svelte と違い「これがUIファイル」という決まりは無いので、**役割で分ける**だけで十分です。

## 6. git の基本

**git** は変更履歴を記録する道具。開発機と実行機が同じ端末なので、**こまめな記録と別の場所へのバックアップ**が命綱になります（`../開発/7_注意点と運用.md`）。

```bash
# 最初の1回だけ: 名前とメールを設定
git config --global user.name "あなたの名前"
git config --global user.email "you@example.com"

# プロジェクトのフォルダで、履歴づくりを始める
git init

# いまの状態を見る（何が変わったか）
git status

# 変更の中身を見る
git diff

# 「これを記録する」と選ぶ（ステージ）
git add Product.swift Cart.swift RegisterView.swift

# 記録する（コミット）
git commit -m "レジ画面: 商品パネルとカートを表示"

# 履歴を見る
git log --oneline

# 直前の記録だけ見る
git show
```

**コミットは小さく、メッセージは短く具体的に**。「何を変えたか」が後で分かるようにします。

### 見せたくない・入れなくないファイル

ビルドで自動生成されるもの、端末ごとの設定、**秘密**は履歴に入れません。`.gitignore` というファイルに書きます。

```gitignore
# macOS
.DS_Store

# Xcode が作るもの
DerivedData/
build/
*.xcuserstate
xcuserdata/

# 秘密（鍵・トークン・個人の署名情報）
*.p12
*.mobileprovision
Secrets.swift
```

- **秘密情報は絶対にコミットしない**（APIキー、パスワード、署名の鍵）
- 一度コミットすると履歴に残る。**入れる前に** `.gitignore` を用意する
- 取り消したいときは `git restore ファイル名`（まだ `add` していない変更を戻す）。**`add` 後**なら `git restore --staged` してから

> git は必須ではありませんが、Macが来たら `git init` して、**変更のたびにコミット**する習慣をつけると、壊れたときに戻せます。ソース・原本は**別の場所**にもバックアップします。

## 7. 再ビルド・再導入・署名7日

| 項目 | 内容 |
| --- | --- |
| ビルドと実行 | Xcodeで **`⌘R`**（Product > Run）。開発機と実行機が同じNeoなので、そのまま起動する |
| きれいにして再ビルド | **`⇧⌘K`**（Product > Clean Build Folder）→ `⌘R` |
| 署名 | 無料の Personal Team を使う。**有効期限は7日として扱う**（A-16）。切れると起動できなくなる |
| 更新の反映 | コードや**画像**を変えたら**再ビルド**が必要。**商品マスタCSV**の更新は再ビルド不要 |
| 再導入後 | 端末内のデータ（商品マスタ・販売・在庫）が**残っているか**を確認する（A-16） |

**7日の対策**（使い方の注意）:

- 営業日の**前に**再ビルド・再導入する**日程を確保**する（当日慌てない）
- 切れてから直すのではなく、**余裕をもって**入れ直す
- 再導入後は、起動して**会計を1件テスト**し、在庫・販売が想定どおりかを確かめる

**再導入の手順（おおまか）**: NeoをMacとして接続（または同じ端末で作業）→ Xcodeで対象を選ぶ → `⌘R`。

## 8. 実機確認の勘所

本番（Neo）で使う前に、次の点を**実際に触って**確かめます。

- **通信を切って**動くか（Wi-Fiオフ／機内モード）: 商品登録・QR読み取り・手動入力・商品パネル・カート編集・合計の算出・画像表示・**現金会計**・中断・取消・在庫・集計・エクスポート（A-10）
- **カメラの許可**: QR読み取りでクラッシュしたら、ほぼ**許可の設定漏れ**
  - **macOS**: `Signing & Capabilities` の `App Sandbox` → `Camera` にチェック。`Info`（または `Info.plist`）に `NSCameraUsageDescription`（日本語の説明）
  - **iOS/iPadOS**: `Info` に `NSCameraUsageDescription`
- **QRが読みにくい**: 商品パネル・ID手動入力で代替できる。ラベルの大きさ・コントラストを調整
- **スリープ・画面ロック**: 営業中は無効にする（システム設定。Neoでの項目は実機で確認）
- **アプリ切替のあと**: レジ ⇄ WoS を往復し、**カメラが再開するか**、状態が復元されるかを確認
- **クラッシュしたら**: Xcodeの Console か、Macの **Console.app**、または `Window > Devices and Simulators` のログを見る。赤いメッセージの**上から数行**が手がかり

**できた合図**:
- 赤いエラーを1つずつ潰して、最後に**ビルドが通る**（`Build Succeeded`）
- ブレークポイントで止めて、Variables view と `po` で**値が読める**
- `git log --oneline` に、作業ごとのコミットが並ぶ
- 通信を切った状態で、**追加 → 現金会計 → 在庫まで**通る

## ポイント

- エラーは**一番上の赤**から。ファイル名・行番号・型名を読む。消えない赤は Clean（`⇧⌘K`）して再ビルド
- 調査は `print`（手軽）→ **ブレークポイント＋lldb**（強力）。確認用の `print` は `#if DEBUG` で囲むか消す
- アプリは**複数ファイル**に分ける。同じターゲットなら `import` 不要。**メンバーシップ**に注意
- git は**こまめにコミット**。`.gitignore` で**生成物と秘密**を除外。秘密は**絶対に入れない**
- **署名は7日で失効**。営業日**前**に再導入する日程を確保し、再導入後にデータが残るか確認（A-16）
- 本番前に、**通信を切って**一通り動作確認する（A-10）
